# ADR-002: 结构化输出采用三级降级策略 + 统一 Zod 校验出口

## Status
Accepted (2026-08-04)

## Background
审计发现阻断级缺陷（tech-spec BLOCKER-1）：mock 路径返回**对象**，真实 LLM 路径返回**字符串**，
而下游一律按对象消费——
- `engine.js:112` `content.questions?.length` → PRECHECK 门禁静默失效；
- `engine.js:118` `content.level` → 改动等级永不回填；
- `engine.js:119` `content.rationality?.verdict` → AI 澄清闭环永不触发；
- `ReqDetail.tsx:66` `JSON.parse` 抛错回退纯文本 → 评估视图整块不渲染。

即"打开真实 LLM 后系统静默退化"，且不报错。

同时调研确认：各家「OpenAI 兼容」对 `response_format` 支持度分化严重——
DeepSeek/GLM/通义仅支持 `json_object` 且 **prompt 必须含 "json" 字面量否则 400**；
腾讯混元/MiniMax 完全无 `response_format`；Anthropic 走 `output_config.format`（已 GA）。
不存在一套代码打通所有 Provider 的可能。

## Decision
按 Provider 能力矩阵做**三级降级**，且**无论走哪级，出口一律过同一个 Zod schema 校验**：

- L1 原生强约束：Anthropic `output_config.format`；OpenAI/Kimi `response_format.json_schema`
- L2 弱约束：`response_format={type:'json_object'}`，并**自动确保 prompt 含 "json" 字面量**以规避 400
- L3 纯提示词兜底：schema 内嵌 prompt + 抽取首个 JSON 块 + 校验失败带错误重试 1 次

校验不通过 → 降级 mock 并记录 `degraded_reason='schema_validation_failed'`。

适用范围：`PRECHECK` / `EVALUATE` / `TEST_CASE` 强制结构化；
`PRD_GEN` / `DEV_PROMPT` 产物本身是 Markdown，**保持字符串**，不为统一而统一。

## Consequences
正面：
- `engine.js` 拿到的永远是合法对象，BLOCKER-1 根治；
- 前端 `JSON.parse` 恒成功，评估视图稳定渲染；
- 支持无 JSON 能力的 Provider（混元/MiniMax）而不牺牲契约。

负面：
- L3 路径有额外重试开销与 token 成本；
- 需为 3 个 action 维护 Zod schema，schema 变更需前后端同步（通过 openapi.yaml 收口）。
