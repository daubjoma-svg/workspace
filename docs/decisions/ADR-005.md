# ADR-005: GitLab 同步采用串行队列 + 令牌桶，一期不做定时全量刷新

## Status
Accepted (2026-08-04)

## Background
GitLab 官方文档明确：repository archive 下载限流 **5 次/分钟/用户**，
GitLab.com **不可配置**（自建实例管理员可关闭）。

现状 `gitlab.js:72` `syncModule()` 为即时同步，`admin.js:165` 直接 await 执行，无队列、无限流、无退避。
模块数超过 5 时，批量同步必然触发 429，同步状态长期挂 FAILED。

另审计出三项相关缺陷：
- `gitlab.js:81` 仅传 `sha`，**全量下载整仓**，未使用官方支持的 `path` 参数下推子路径（monorepo 场景数量级浪费）；
- `gitlab.js:82` `Buffer.from(await res.arrayBuffer())` 把整个 tarball 读进内存，GB 级仓库直接 OOM；
- `execSync`/`readFileSync`/递归 `walk` 全同步，单进程 Express 在解压期间**全站无响应**。

## Decision
1. 同步由「即时执行」改为「**入队**」语义：`POST /modules/{id}/sync` 返回 `202 + task_id`，
   前端轮询 `GET /sync-tasks/{id}`。新增 `sync_tasks` 表承载。
2. 队列**单并发串行**，令牌桶间隔 >= 12s/次；遇 429 读 `Retry-After` 退避，最多重试 3 次。
3. UI「全部同步」改为排队提示（"已加入队列，预计 N 分钟完成"），不伪装成即时操作。
4. **一期不做定时自动全量刷新**——会周期性撞限流。只做手动触发 + 单模块。
5. `sub_path` 非空时下推到服务端 `?path=<sub_path>`；老版本 GitLab 不支持则回退全量下载 + 本地裁剪。
6. 下载前查 `Content-Length` 预检，落盘上限默认 200MB，解压后文件数上限 20000，超限标 FAILED。
   优先流式下载而非全量 buffer。
7. 解压与文件遍历异步化（`spawn` + `fs.promises`），避免阻塞事件循环。

## Consequences
正面：不再撞限流；大仓不会 OOM 或卡死全站；monorepo 场景大幅省流量与磁盘。

负面：
- 同步从"点了就好"变成异步任务，前端需增加轮询与状态 UI；
- 多模块同步总耗时线性增长（6 个模块 >= 60s），属限流下的物理下限，需在 UI 上如实告知。
