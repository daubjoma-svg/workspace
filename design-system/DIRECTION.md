## 0. 设计寄存器与三轴刻度（先定坐标，再定视觉）

| 项 | 结论 | 依据 |
|---|---|---|
| **设计寄存器** | **Product 寄存器**（设计服务产品，不是设计即产品） | 本品是企业内部研发协作工具（需求池/看板/流转/AI 产物审阅），标杆是"赢得熟悉感"——让 Linear / 飞书项目 / GitLab 的老用户第一眼觉得可信，而不是追求独特性 |
| **平台轴** | web（桌面优先，1440 基准），响应式下探至 768/375 | 企业内网 PC 端为主场景，移动端为查看+审批的轻量场景 |
| **DESIGN_VARIANCE** | **3 / 10**（可预测） | 工具型后台，布局的可预测性直接换算成操作效率。禁止非对称炫技，禁止 Masonry。栅格严格 12 列 |
| **MOTION_INTENSITY** | **3 / 10**（功能性） | 采纳 Vercel Geist 纪律："0ms 往往是最好的选择"。动效只用于表达空间关系与状态确认，禁止装饰性循环动画 |
| **VISUAL_DENSITY** | **7 / 10**（驾驶舱偏上） | 需求列表/看板/时间线/AI 长文产物/代码影响面，信息密度是核心竞争力。**禁止用通用卡片盒子包一切**，改用 `border-top` / `divide-y` / 负空间分组 |

**一句话定调**：
> 蓝晒图的冷静 + 游标卡尺的精准 + 调度室大屏的秩序。
> 深冷蓝墨作单一强调色，中性灰承担 90% 画面，AI 用「虚线材质」而非「彩色」来标识。

## 1. 对标品牌（联网调研 4 个，逐个提取可落地结论）

### 1.1 Linear — 主对标（状态流转 + 克制强调 + 亮度阶梯）
调研来源：linear.app / opendesign.cc 设计系统拆解 / lobehub design-md-linear

| 可迁移的做法 | 我们怎么用 |
|---|---|
| 单一 accent（`#5e6ad2`）只出现在 CTA / 激活态 / 品牌位，其余全靠白色不透明度分级 | **锁定"每屏 ≤2 处可见 accent"**，需求等级/优先级不用彩色块，用字重+边框 |
| 深色以「亮度阶梯」而非阴影表达层级：`#08090a → #0f1011 → #191a1b → #28282c` | 深色主题照搬这套方法论（不照搬色值），四级 surface 阶梯 |
| Inter Variable + 特征字重 **510**（介于 regular 与 medium），display 尺寸激进负字距 | 采纳三级字重 400/510/590；中文静态字体回退 400/500/600 |
| 超薄半透明边框 `rgba(255,255,255,0.05~0.08)` 构建结构，不制造噪音 | 深色主题边框全部走半透明白，不用实色灰 |
| 严格 4px 网格；动效 150ms micro / 400ms medium | 采纳 4px 网格；动效更激进收敛（见 §6） |
| **我们不学**：indigo-violet 品牌色（`#5e6ad2`/`#7170ff`）——它是紫系，且已被大量 AI 产品抄成模板 | 主色改走「蓝晒工程蓝」，见 §3 |

### 1.2 Vercel Geist — 副对标（信息优先 + 圆角纪律 + 动效纪律）
调研来源：designsystems.one / seedflip Geist 拆解 / sotasync Geist 开源解读 / open-design.ai

| 可迁移的做法 | 我们怎么用 |
|---|---|
| **"颜色是用来传达信息的，而非装饰"**——accent 只出现在①系统状态反馈②当前页最重要的那一个操作 | 写进 DESIGN.md §7 Do's & Don'ts 第一条 |
| **圆角只有三档，全产品统一不混用**（6 / 12 / 16） | 直接采纳（现有代码有 7/8/9/10/11/12/16 七档混用，Phase 3 必须收敛） |
| **动效原则："0ms 往往是最好的选择"** | Tab 切换、筛选、排序一律 0ms；只有位移/浮层保留过渡 |
| tabular numerals 贯穿表格、日志、指标 | 需求单号、工时、Token 消耗、耗时统计全部 `font-variant-numeric: tabular-nums` + mono |
| shadow-as-border：`box-shadow: 0 0 0 1px rgba(0,0,0,.08)` 替代 border | 采纳于卡片/输入框，避免 box model 抖动 |
| 所有标题 letter-spacing 为负，字号越大越紧 | 采纳（见 §4 字距表） |
| **官方警告**："直接照搬会做成 Vercel 克隆" | 因此我们**不用** Geist 的纯黑白双色系，保留一个功能性蓝作 accent；也不用 Geist 的 workflow 三色（Ship Red/Preview Pink/Develop Blue） |

### 1.3 飞书项目 — 中文场景对标（多视图 + 节点流转控件 + 信息密度）
调研来源：project.feishu.cn 帮助中心（认识飞书项目 / 看板视图 / 表格视图）

| 可迁移的做法 | 我们怎么用 |
|---|---|
| 四视图并存：**表格 / 列表 / 看板 / 甘特**，同一数据不同组织方式 | 一期做**表格 + 看板**双视图（已有雏形），二期补甘特；视图切换用分段控件常驻工具条 |
| **表格行高可切换**（紧凑/适中/高/超高） | 采纳"密度切换"：紧凑 36px / 适中 44px，存 localStorage。这是密度 7 的合法出口——让重度用户自己调 |
| 表格内**直接流转节点**（有权限才可点）、双击单元格改字段值 | 需求列表页支持行内流转，权限不足则不渲染入口（与 D8 决策一致） |
| 看板支持多级分组（纵向看板栏 + 横向泳道） | 一期：纵向按 SOP 节点分列；泳道留接口 |
| 视图右下角常驻**汇总卡**（总数/完成进度/平均完成时长/各节点停留时长） | 直接抄这个信息位——它比顶部四个统计卡更省空间，符合密度 7 |
| 流程图直观展示标准化协作流程，让协作者掌握上下游 | PRD 要求的流程图落地为「需求流转条」组件（见 §7） |
| **我们不学**：飞书的多彩标签体系（每个字段一个颜色）——会击穿"每屏 ≤2 处 accent" | 标签统一走中性色 + 1px 边框，仅 P0/阻塞/失败三种状态允许语义色 |

### 1.4 GitLab / TAPD — 补充参考（代码感知 + 自动化规则）
调研来源：ones.com.cn 研发管理工具测评 / tapd.cn 看板深度解析

- Linear 与 GitHub/GitLab **双向同步**：提交代码/合并 MR 自动关闭任务，代码中可直接引用任务 ID → 我们的 GitLab 代码感知要有对应 UI：需求详情页的「代码影响面」区块（仓库/分支/模块/文件数/关联提交），mono 字体呈现。
- TAPD「AI 自动化规则」把 AI 定位成规则引擎而非聊天框 → 我们的 AI 节点同理：**AI 是流程上的一个工位，不是右下角一个聊天气泡**。

## 2. 设计语言：「Blueprint Calm · 蓝图冷静」

三个品牌声音词（物理对象，非形容词）：
1. **蓝晒图纸**（cyanotype blueprint）—— 冷、蓝、线条即信息
2. **游标卡尺**（vernier caliper）—— 刻度精准、金属中性、数字可读
3. **调度室大屏**（dispatch board）—— 高密度、状态一眼可辨、无装饰

落地为四条视觉法则：

| # | 法则 | 具体约束 |
|---|---|---|
| L1 | **线条即结构** | 用 1px 线（border/divide）建立层级，而不是用卡片盒子和阴影。列表/详情内部一律 `divide-y`，禁止把每一行包成 card |
| L2 | **颜色即信息** | 中性色 ≥90%；accent 每屏 ≤2 处；语义色仅 3 个（成功/警告/危险），且只用于状态，不用于分类 |
| L3 | **数字用等宽** | 单号、工时、等级、Token、耗时、日期全部 mono + tabular-nums。这是"工程可信度"的最低成本来源 |
| L4 | **AI 用材质区分，不用颜色区分** | 见 §5，这是本产品最重要的差异化决策 |

**Light-first**：默认浅色（企业内网白天办公主场景 + 中文长文阅读），深色为**完整对等主题**（不是浅色反色），由用户或系统偏好切换。

## 3. 配色方向（A1-identity）

### 3.1 强调色：Cyanotype Blue `#0E62A8`

- HSL(207°, 85%, 36%) —— 冷、偏青、低明度的工程蓝墨
- **为什么不是现有的 `#2563EB`**：`#2563EB` 是 Tailwind `blue-600` 原值，与 Indigo `#6366F1` 一样属于"训练数据默认色"，一眼 AI
- **为什么不是 Linear 的 `#5e6ad2`**：紫系 indigo-violet，已被 AI 产品抄烂，且逼近 P0-2 红线区
- 对比度实测（WCAG 2.1 相对亮度公式）：

| 组合 | 比值 | 判定 |
|---|---|---|
| `#0E62A8` 文字 on `#FFFFFF` | **6.30 : 1** | AA ✓（正文/链接可用） |
| `#FFFFFF` 文字 on `#0E62A8` 按钮 | **6.30 : 1** | AA ✓（主按钮可用） |
| 深色态 `#4FA6EE` on `#0E1116` | **7.23 : 1** | AAA(大字) / AA ✓ |

### 3.2 浅色主题（默认）

```css
:root {
  /* A1-identity */
  --bg:            #F5F7FA;  /* 冷调纸面，非奶油非米色（避开 warm-neutral 禁区） */
  --surface:       #FFFFFF;
  --fg:            #101724;  /* 近黑带蓝铸调，非纯黑 */
  --muted:         #5D6B7E;  /* 5.05:1 on --bg ✓ 12px 元数据安全线 */
  --accent:        #0E62A8;
  --border:        #E2E7EE;

  /* B-slot */
  --surface-2:     #EEF2F6;  /* 表头、内嵌块、hover 底 */
  --fg-2:          #3C4859;  /* 正文次级（≈9:1） */
  --meta:          #7A8798;  /* 3.40:1 —— 仅图标/分隔/≥16px 弱化文本，禁止 12px 正文 */
  --border-soft:   #EFF2F6;
  --border-strong: #CBD3DE;

  /* A2-semantic（全部实测 ≥4.9:1 on white） */
  --success:       #12805C;  /* 4.92:1 —— 深松绿，非 Tailwind green-600 */
  --warn:          #B45309;  /* 5.02:1 —— 深琥珀 */
  --danger:        #B3261E;  /* 6.53:1 —— 砖红 */
  --accent-on:     #FFFFFF;
  --accent-hover:  color-mix(in srgb, var(--accent) 90%, #000);
  --accent-active: color-mix(in srgb, var(--accent) 82%, #000);
  --accent-wash:   color-mix(in srgb, var(--accent) 8%, transparent);
}
```

### 3.3 深色主题（对等，非反色）—— 亮度阶梯法（学 Linear 的方法，不抄色值）

```css
:root[data-mode="dark"] {
  --bg:            #0E1116;
  --surface:       #151A21;
  --surface-2:     #1C222B;
  --surface-3:     #262E39;  /* hover / 抬升 */
  --fg:            #E9EEF5;
  --fg-2:          #C3CCD9;
  --muted:         #8B97A6;
  --meta:          #626D7B;
  --border:        rgba(255,255,255,0.07);
  --border-strong: rgba(255,255,255,0.12);
  --accent:        #4FA6EE;
  --accent-on:     #06121D;   /* 深色态主按钮反色（Linear/Vercel 通用模式） */
  --success:       #35B37E;
  --warn:          #D9973E;
  --danger:        #E5645C;
}
```

**配比铁律**：中性 70–90% / accent 5–10% / 语义 0–5% / 效果色 <1%。

### 3.4 明确禁用清单（配色层）

- ❌ 任何 Indigo→Pink / 紫→粉渐变（P0-2）
- ❌ Tailwind 默认 `#6366F1`、`#2563EB` 作为品牌强调色
- ❌ 奶油/米色/沙色背景（OKLCH L 0.84–0.97, C<0.06, hue 40–100 全带禁用）
- ❌ 用颜色给需求「分类」（业务线/模块/产品线一律中性标签）

## 4. 字体方向

### 4.1 现状问题（必须换）
现有 `body { font-family: "Plus Jakarta Sans", ... }` —— **Plus Jakarta Sans 在反射拒绝字体列表中**（训练数据默认值，制造 monoculture）。Phase 3 必须替换。

### 4.2 字体栈决策

| 角色 | 字体 | 授权 | 理由 |
|---|---|---|---|
| **Display**（页面标题 H1/H2、统计数字、Hero 数值） | **Geist Sans** | OFL，可自托管 | 工程精度感 + 天然 tabular numerals + 大字号负字距压缩感。避免"Inter 直出"的通用相 |
| **Body**（正文、表格、表单、导航、按钮） | **Inter**（开启 `cv01` `ss03` `tnum`） | OFL | 13–14px 高密度界面下可读性天花板。作为 body 使用合规（禁令仅限"拿 Inter 当 display 声称高级"） |
| **中文** | **Noto Sans SC**（思源黑体），回退 `PingFang SC` / `Microsoft YaHei` | OFL | 与 Inter/Geist 的 x-height 与字重轴匹配度最好；企业内网需 subset 自托管（约 1.2MB → 分包按需） |
| **Mono**（单号、分支、commit、diff、时间戳、Token 数、模型名） | **JetBrains Mono** | OFL | 0/O、1/l 区分度高，代码感知场景刚需 |

配对数量核算：Display(Geist) + Body(Inter) = 2 种，Mono 不计入 → **合规**（上限 2 配对）。

### 4.3 字号阶梯（8 级，桌面基准）

| Token | px / rem | 行高 | 用途 |
|---|---|---|---|
| `--text-xs` | 12 / 0.75 | 1.5 | 元数据、时间戳、徽章 |
| `--text-sm` | 13 / 0.8125 | 1.55 | 表格单元格、次级说明（密度 7 主力尺寸） |
| `--text-base` | 14 / 0.875 | 1.6 | 正文、表单、按钮 |
| `--text-md` | 16 / 1 | 1.7 | AI 产物长文正文（中文阅读安全线） |
| `--text-lg` | 18 / 1.125 | 1.4 | 卡片标题、需求标题 |
| `--text-xl` | 20 / 1.25 | 1.35 | 区块标题 |
| `--text-2xl` | 24 / 1.5 | 1.25 | 页面标题 H1 |
| `--text-3xl` | 32 / 2 | 1.15 | 统计大数字（仅 Dashboard） |

> ⚠️ 现有代码存在 `13.5px / 12.5px / 11.5px / 14.5px` 等半像素字号（8 处以上），Phase 3 必须收敛到上表 8 级。

### 4.4 字重与字距

- 字重三级：**400**（正文）/ **510**（表格表头、按钮、小标题）/ **590**（页面标题、强调）
  - 可变字体走 400/510/590；`Noto Sans SC` 静态回退 400/500/600
- 字距规则：
  | 场景 | letter-spacing |
  |---|---|
  | 正文 14–16px | `0` |
  | 小字 12–13px | `0.01em` |
  | **ALL CAPS 标签**（表头、section 标题） | **`0.06em`**（现有代码为 `.4px`/`.5px`，需换算为 em） |
  | 标题 ≥24px | `-0.015em` |
  | 展示数字 ≥32px | `-0.025em` |
- 中文段落：`text-wrap: pretty`；正文行长 ≤ 38 中文字符

## 5. AI 节点的视觉语言（本产品最重要的差异化决策）

**问题**：市面所有 AI 产品都用「紫色 / 渐变 / 星星图标 / 光晕」标识 AI。这既踩 P0-2 红线，也毫无辨识度。

**我们的方案：AI 用「材质」区分，不用「颜色」区分。**

| 语义 | 视觉编码 | 理由 |
|---|---|---|
| **AI 生成、待人工确认** | **1px dashed 边框** + 冷灰底 `--ai-surface` + 左上角 mono 小标签 `AI · 评估` | 虚线 = 草稿/未定稿，是设计界通用共识（Figma 的未确认、CAD 的辅助线），语义天然正确 |
| **人工已确认** | **1px solid 边框** + `--surface` 白底 + 确认人头像 + 时间戳 | 实线 = 定稿。虚→实的转变本身就是"人在环"的视觉隐喻 |
| **AI 生成中** | 虚线边框 + 骨架块逐段浮现（非打字机） | 打字机效果在长文档场景是负体验，逐段浮现更快可读 |
| **AI 失败/超时** | 虚线边框 `--danger` + 具体错误 + 重试按钮 + 降级选项（换模型/手动填写） | 5 态覆盖的 Error 态 |
| **AI 元信息** | mono 小字：模型名 / 耗时 / Token 数 / 成本 | 工程可信度来源，也是成本管控入口 |

C-extension token（本项目专属，仅 3 个）：
```css
--ai-surface:  #F7F9FB;   /* 浅色态：比 --bg 更冷更淡的"机器纸" */
--ai-ink:      #3D4654;   /* AI mono 标签色，石墨中性 */
--ai-dash:     #C3CCD8;   /* 虚线边框色 */
/* 深色态 */
--ai-surface:  #12171E;  --ai-ink: #9AA6B4;  --ai-dash: rgba(255,255,255,0.14);
```

**明令禁止**：AI 节点不得使用紫色、渐变、发光边框、毛玻璃、✨/🤖 任何 emoji。

## 6. 图标系统（锁定，需 architect 确认）

| 项 | 决策 |
|---|---|
| **图标库** | **Lucide**（`lucide-react`），ISC 许可，1500+ 图标 |
| **为什么** | ①24px 网格 stroke 图标，与 Inter/Geist 的线条重量匹配；②`lucide-react` 支持 tree-shaking，按需 import 不炸包体；③shadcn/ui 事实标准，未来若引入组件库无需二次迁移；④现有代码已是手写 stroke SVG，迁移语义一一对应，成本最低 |
| **落选** | Tabler（4900+ 但 React 包体大、部分图标风格不齐）；Phosphor（多 weight 反而增加不一致风险）；Heroicons（数量不足，缺研发流程语义如 git-branch/git-merge/workflow） |
| **尺寸** | **16px**（行内/表格/标签）、**20px**（按钮内/导航）、**24px**（独立图标/空态），仅此三档 |
| **描边** | `strokeWidth={1.75}` 全局统一（16px 下比 2 更细腻，比 1.5 更清晰） |
| **颜色** | 继承 `currentColor`，不单独指定；禁止彩色图标 |
| **无障碍** | 纯图标按钮必须 `aria-label`；装饰性图标 `aria-hidden="true"` |

**关键语义映射（研发流程场景）**：
`需求` FileText · `看板` LayoutGrid · `列表` Table2 · `流程` Workflow · `AI 节点` Sparkles→**改用** `Cpu`（避开 AI 套路星星）· `代码` GitBranch / GitCommitHorizontal / GitMerge · `测试` FlaskConical · `上线` Rocket→**改用** `CircleCheckBig` · `客户` Building2 · `搜索` Search · `设置` Settings2 · `打回` Undo2 · `确认` Check

### 12.1 闭环流程图节点区分 —— 锁定「材质 + 形状」而非「颜色」（与 PM mermaid 配色有意分歧）

> ✅ **已裁决（2026-08-04，team-lead 确认）**：正式采用本「材质+形状」正交法，PM mermaid 三色方案不采用。理由见 team-lead 裁决：① 守住 Blueprint Calm 核心法则「AI 用材质不用颜色」；② 避免绿=AI 与 success=绿 撞色、琥珀=网关 误读为告警；③ 守住「每屏≤2 处 accent」预算。本分歧记录作为决策留痕保留，前端据 DESIGN.md §4.5 FlowBar 实现 F8。

PM 在 mermaid 里用三色底区分节点类型（人工 `#e8eef7/#1e3a5f` 蓝、AI `#e6f4ee/#0f766e` 绿、网关 `#fef3e2/#b45309` 琥珀）。我**不采用**这套三色方案，改用「材质 + 形状」区分，理由如下：

1. **语义冲突**：`enterprise.md` 原文语义色定义是「绿=通过 / 红=拒绝 / 蓝=进行中 / 灰=草稿」，并未定义"绿=AI"。把 AI 染绿会与"通过/success"语义撞色——一个 AI 节点跑完（绿=通过）又是 AI（绿=AI），双重绿意无法区分"AI 类型"与"执行成功"。
2. **琥珀同理**：网关常态是流转中的正常判定点，不该默认就挂"待关注/警告"色（琥珀是告警语义）。只有网关判定为"否/打回"时才该出现警示色。
3. **密度 7 的色彩预算**：流程图在密度 7 的详情页只是其中一个组件，再引入绿+琥珀两个图例色会击穿"每屏 ≤2 处 accent"的预算。

**锁定方案（节点类型轴 × 状态轴 正交，互不干扰）**：

| | 人工节点 H | AI 节点 AI | 判定网关 G |
|---|---|---|---|
| **类型信号（恒定）** | 实线圆环 1px `--border-strong` | **虚线圆环** 1px `--ai-dash` + 冷灰"机器纸"底 `--ai-surface` + 圆内 mono 字标 `AI` | **菱形**（形状区分，不靠颜色） |
| **未到达** | 灰底 + `--meta` 文字 | 同左，但虚线 | 灰底菱形 |
| **当前** | `--accent` 环 + 3px halo | `--accent` 环 + 3px halo（虚线保留） | `--accent` 描边菱形 |
| **已完成** | 实心 `--success` + Check 图标 | 实心 `--ai-ink`（石墨）+ Check 图标 —— **不用 success 绿**，避免与"通过"混淆 | 实心 `--accent`（判定=是）或 `--danger`（判定=否/打回） |
| **曾被打回** | `--danger` 虚线圆环 + 红点角标，悬浮看原因/操作人 | 同左 | 打回路径用 `--danger` 虚线连线，悬浮看原因 |

**打回路径**：用 `--danger` 虚线连线 + 起止角标，悬浮 popover 显示 `{打回人} · {时间} · {原因}`。这条虚线是"路径"层级的，与节点类型层级的虚线（AI 材质）语义不同，靠颜色（红 vs 石墨）区分，不会混淆。

> 这套方案对 F8 验收「已完成/当前/未到达/曾被打回四态一眼可辨」+「AI 与人工视觉可区分」全部满足，且不新增图例色。已锁定，Phase 2 据此出高保真。
